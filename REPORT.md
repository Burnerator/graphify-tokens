The rubric (**5–8 items**: 8 for three PRs, 5 for #3389) is derived statically from the diff, not from the graph: **up to 3** changed Python files under `httpx/`, **up to 3** touched symbols (functions or classes whose definition span, body included, contains a changed line; AST; first three alphabetically), and **up to 3** other package files that mention the most distinct touched symbols as whole words (`git grep -lw`, one count per file and symbol; not a call-graph analysis). It measures whether the review mentions these, not whether it finds bugs or is correct.

### Run design and order

- **v1** (`runs/2026-11-17`): two invocations into the same directory: first `--reps 1` (rep 0), then `--reps 3`, which skipped the completed sessions and ran reps 1-2 (the recorded order indices match `--reps 1` for rep 0 and `--reps 3` for reps 1-2). `base` and `rules-generic` alternate within each question-rep pair (`environment.json` records the last start, 11:17 UTC).
- **v2** (`runs/2026-11-18`): 3 invocations into the same directory, from `environment.json`:
  1. started 07:44 UTC: tasks A and B, 3 reps, claude: rules-official, hooks, strict; codex: rules-official.
  2. started 09:22 UTC: task B, 3 reps, claude: base; codex: base.
  3. started 09:37 UTC: task A, 1 rep, claude: base; codex: base.
  The first base invocation started 98 minutes after the start of the first invocation (not after its task B part). Within an invocation, condition order alternates per question and rep; across invocations it does not.
- Start times of the v2 Claude sessions (first recorded timestamp in each trace, UTC; Codex traces carry no timestamps; pilot copies excluded):
  - task A, base: 09:38–09:43 (8 sessions)
  - task A, graphify: 07:44–08:55 (72 sessions)
  - task B, base: 09:22–09:37 (11 sessions)
  - task B, graphify: 08:58–09:21 (33 sessions)
- A pilot (`runs/pilot-v2`, identical code and conditions, run before invocation 1; its `environment.json` records only its last start, while its Claude traces start earlier, so it was restarted at least once) was copied into the v2 directory, so later invocations skipped those sessions. Its records are **byte-identical copies** (checked when this report was generated) and are counted **once** in the totals above. The pilot's *planned* order interleaved the conditions, but its Claude traces show what actually ran: base started 07:42–07:42 UTC; graphify started 07:31–07:32 UTC, so in practice the graphify sessions also ran before the base session there (Codex traces carry no timestamps).

### Agents and controls (as implemented)

- Claude Code: `claude -p --output-format stream-json`, model alias `sonnet`, `--max-budget-usd 1.50`, no session persistence, `--disallowedTools Agent Task WebSearch WebFetch Write Edit`, `--allowedTools Read Grep Glob` plus Bash patterns for `graphify`, the wrapper, `ls` and `git diff/log/show`. The allow-list only pre-approves those tools; it does not forbid others. The operator's global Claude Code settings also applied, and the traces show Claude running other shell commands through Bash in every condition (e.g. `grep`, `sed`, `test`; `find` and a `python3 -c` one-liner in some base sessions).
- Codex: `codex exec --json --ephemeral -s read-only`, CLI default model.
- Both agents inherited the operator's environment and global configuration (settings, plugins, connectors, a global SessionStart hook with empty output). The configuration was not changed between conditions, but the set of tools Claude reported was not constant over the runs (see the tool-set sensitivity check); the names are redacted from the published traces.
- In v2, `graphify` on the agents' `PATH` is a shim (`work/bin/graphify`) to `scripts/graphify-safe.sh`, an allow-list wrapper (`update`, `query`, `path`, `explain`, `section`) that runs graphify with a stripped environment and no LLM backend. The shim only changes what a bare `graphify` resolves to: the real binary remained reachable by absolute path, and the Codex `rules-official` hook file installed by graphify points at it (`hook-check`, a no-op). In v1 the instructions named the wrapper by its explicit path and the agents kept the caller's `PATH`.
- Claude hooks run graphify's real `hook-guard` through `hookwrap.sh` (unchanged input/output, minimal environment), which logs each firing to `sessions/<id>.hooks.tsv`. These are the **instrumented hook firings**; other hooks (the operator's global SessionStart hook) appear only in the traces.
- Official installers ran inside throwaway corpus copies with a fake `HOME`; the harness aborts if an installer leaves any file in that fake `HOME`. It does not monitor other locations.

### What is measured

- **Successful session completion**: the agent reached its success terminal event (Claude `result` without `is_error`; Codex `turn.completed`) and reported no terminal error event (recoverable events such as Claude's `api_retry` are allowed). The published runs predate exit-code recording; the harness now also requires exit code 0 and retries failed sessions on resume.
- **Total tokens** = uncached input + cache read + cache write + output, as reported by each agent's own event stream. Claude: the per-model token counts of the final `result` event (`modelUsage`), summed over **all** models the session used (the main model and small auxiliary calls). The top-level `usage` field is not used; it can differ from `modelUsage` even for the main model. Codex: the sum over `turn.completed` events, where `input_tokens` includes the cached part, so uncached = `input_tokens − cached_input_tokens`.
- **Uncached in+out** = uncached input + output (excludes cache reads and cache writes).
- **Cost** = Claude's API-equivalent `total_cost_usd`. Not billed: the runs used a subscription login. Codex reports no cost.
- **graphify used** = share of sessions with at least one *successful* graphify command (see the graph-use table for attempted vs successful).
- **Hook fires / denials** = instrumented hook firings from the `hookwrap.sh` logs.
- **Rubric** = share of rubric regexes (case-insensitive) found in the final answer.
- `experiment_v2.py sanitize` recomputes the token, status, answer, rubric, tool and graphify fields of `sessions/*.json` from the **published (redacted) trace** next to it, and the hook counts from the published `hooks.tsv`; wall time and identity fields are kept from the original record. Answers are scored as published (redacted); before publication we checked that tokens, answers' scores and success flags were identical to those computed from the raw traces.
- The graphify counts are **shell-level proxies** detected with a regex over the command text (v2 and v1 alike); output is the serialized tool result, which for `… | head` pipelines is truncated and for `which graphify && …` includes the extra line. A command counts as successful if the shell command exited 0 (Codex) or its tool result was not an error (Claude), even if graphify's own part failed or succeeded inside a mixed command, or graphify printed a diagnostic such as "No node matching" with exit 0. Claude's character counts are the length of the serialized tool result.

## Limitations

- **Small samples.** 3–15 sessions per group; repetitions per condition: `base` v1 (A 3 reps) + v2 (A 1 rep, B 3 reps); `rules-generic` v1 (A 3 reps); `rules-official` v2 (A 3 reps, B 3 reps); `hooks` v2 (A 3 reps, B 3 reps); `strict` v2 (A 3 reps, B 3 reps). No significance testing; read the per-question ratios, their range and the sensitivity tables, not single digits.
- **Batch order, not interleaving, in v2.** Base sessions ran in separate invocations after the graphify conditions (the copied pilot was planned interleaved, but its Claude traces show the same graphify-then-base order); see *Run design and order*. Time-of-day or service-side changes between batches are not ruled out, for task B in particular, which has no independent sensitivity check.
- **Day-to-day drift** (table above) is of the same order as some of the smaller effects; effects of that size are not resolved by this data. v1 and v2 also differ slightly in Claude's pre-approved Bash patterns, so the pooled task A baseline mixes two launch configurations.
- **The operator's normal installation** (global settings, plugins, connectors, a global SessionStart hook) was loaded in every session. It adds context, its permissions let Claude run extra shell commands, and the number of tools it exposed to Claude varied over the runs, unevenly across conditions (see the tool-set sensitivity check). Another installation may give different numbers.
- **Claude and Codex token totals are not comparable with each other**: different models, tokenizers, caching and system prompts. Compare conditions within one agent.
- **The rubric is regex mention coverage**, not a correctness judgement; quality moved by a few points in most cells, but not all: Codex `rules-generic` on anvil went from 93% (pooled base) to 84% (96% → 84% against its own run's base).
- **Mechanism not established.** The data shows token volumes per condition, graph queries and raw reads; it does not show which files each condition read or attribute the difference to the graph output alone.
- **Token volume and API-equivalent cost only**: Claude's cost column is the API-equivalent figure; runs used subscription logins and nothing was billed.
- **Two Python repos** (1.1k and 17.8k lines). graphify says its gains grow with repo size; very large repos are not covered.
- **Graphify Cloud is not tested.** The "80% fewer tokens" headline in graphify's README refers to Graphify Cloud, a hosted product. The open-source README's benchmark measures retrieval quality (key-fact coverage). The open-source docs also describe `graphify benchmark`, which *estimates* per-query token reduction against reading the whole corpus naively (its docs show 83.6× on a code-only httpx graph: https://docs.graphify.com/open-source/features/token-benchmark) and calls itself "a guide to scale, not a billing figure"; this experiment measures what the agents actually consumed end to end, which is a different quantity. Sources are linked in the README.
